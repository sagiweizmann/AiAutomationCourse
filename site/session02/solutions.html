אפיון תהליך ההחזרות — תשובה לדוגמה

As-Is — התהליך כמו שהוא קורה היום

  1. לקוח פונה בוואטסאפ או במייל: "קיבלתי מוצר ואני רוצה להחזיר".
  2. הנציג מחפש את ההזמנה בגיליון ההזמנות לפי שם או מספר.
  3. הנציג בודק ידנית במסמך המדיניות אם ההחזרה מותרת (עד 14 יום, לא הורכב, לא מוצר מותאם אישית).
  4. אם זכאי — שולח הוראות החזרה ומעדכן את הסטטוס בגיליון.
  5. כשהמוצר חוזר למחסן — הנציג מאשר זיכוי ידנית ומודיע ללקוח.

To-Be — תרשים הזרימה (Mermaid)

זה הקוד ש-Claude מחזיר. הדביקו אותו ב-mermaid.live כדי לראות תרשים.

flowchart TD
  A[פניית החזרה נכנסת] --> B{זכאי לפי המדיניות?}
  B -- לא --> C[הודעה מנומסת ללקוח + סיבה]
  B -- כן --> D[שליחת הוראות החזרה]
  D --> E[עדכון סטטוס בגיליון]
  E --> F{המוצר חזר למחסן?}
  F -- כן --> G[אישור זיכוי - נקודת אישור אנושית]
  G --> H[הודעת סיום ללקוח]
✅ צוואר הבקבוקהבדיקה הידנית של הזכאות (שלב 3) — חוזרת על עצמה, תלויה בנציג, ומועדת לטעות. זה גם השלב עם הערך הגבוה ביותר לאוטומציה.

מצאו את הטעות ב-JSON

א' — פסיק חסר בין שתי השורות. הוסיפו פסיק אחרי הערך הראשון:

{
  "name": "רונית",
  "order_id": 50912
}

ב' — גרש במקום מירכאות. מפתח חייב מירכאות כפולות ":

{
  "name": "רונית",
  "order_id": 50912
}

ג' — פסיק מיותר בסוף. אחרי הפריט האחרון אין פסיק:

{
  "name": "רונית",
  "order_id": 50912
}

ד' — מפתח בלי מירכאות. גם המפתח name צריך מירכאות:

{
  "name": "רונית",
  "order_id": 50912
}
✅ הכללמפתחות וערכי טקסט תמיד במירכאות כפולות · בין פריטים פסיק · אחרי הפריט האחרון בלי פסיק · רק מספרים, true/false ו-null בלי מירכאות.

בקשות API אמיתיות ב-Hoppscotch

הבקשהקודהיכן הערך
GET open-meteo (תחזית שבועית באשדוד)200מערכי daily: time, temperature_2m_max/min, precipitation_probability_max
GET frankfurter (שער מטבע)200rates.ILS
POST jsonplaceholder (יצירת רשומה)201התשובה מחזירה את האובייקט + שדה id חדש
GET httpbin200headers / args — איך השרת רואה אתכם

תשובת התחזית מחזירה מערכים מקבילים — אותו מיקום בכל מערך הוא אותו יום (הערכים משתנים בזמן אמת):

{
  "daily": {
    "time":                       ["2026-01-01", "2026-01-02", ...],
    "temperature_2m_max":         [19.8, 21.1, ...],
    "temperature_2m_min":         [11.2, 10.7, ...],
    "precipitation_probability_max": [10, 40, ...]
  }
}
// היום הראשון:  daily.temperature_2m_max[0]  →  19.8°  |  סיכוי גשם  →  daily.precipitation_probability_max[0]  →  10%
✅ ההבדל שחשוב200 = בקשת GET הצליחה (קראנו נתונים). 201 = POST יצר רשומה חדשה. זה בדיוק מה ש-Make בודק אחרי כל קריאה.

Claude מחלץ נתונים ל-JSON

לפנייה של רונית שגב, Claude אמור להחזיר JSON נקי (בלי טקסט מסביב):

{
  "customer_name": "רונית שגב",
  "order_id": "50912",
  "topic": "delivery",
  "urgency": "high"
}

פנייה בלי מספר הזמנה — order_id חוזר null, לא ערך שהומצא:

{
  "customer_name": "נועה",
  "order_id": null,
  "topic": "other",
  "urgency": "low"
}
✅ מה בודקיםJSON בלבד (בלי "הנה התשובה") · אותם שדות בכל פנייה · topic ו-urgency רק מהרשימה הסגורה · שדה חסר = null.

Claude בונה את תוכנית האוטומציה — תשובה לדוגמה

תוכנית סבירה לתהליך ההחזרות. הטבלה היא מה ש-Claude מחזיר; ההערה בסוף היא התוספת האנושית.

#מודולתפקיד
1Webhook (טריגר)פנייה חדשה (טופס / מייל) מפעילה את התרחיש
2Claudeמקבל את טקסט הפנייה, מחזיר JSON: customer_name, order_id, topic, urgency
3Routerמפצל לפי topic: delivery / defect / refund / other
4Google Sheetsמחפש את ההזמנה ובודק זכאות לפי הנתונים
5אישור אנושיבנתיב refund: עצירה לאישור נציג לפני זיכוי
6Email / WhatsAppשליחת תשובה ללקוח ועדכון הסטטוס בגיליון
✅ נקודות שחייבות להופיעטריגר ברור (Webhook) · Claude מחזיר JSON · נקודת אישור אנושית לפני פעולה כספית · טיפול בקודי שגיאה (401 מפתח, 404 רשומה, 429 יותר מדי בקשות → retry).
הערה אישית לדוגמה"הייתי מוסיף שלב שמודיע ללקוח שהפנייה התקבלה כבר בשנייה הראשונה, עוד לפני הבדיקה — כדי שלא ירגיש שאף אחד לא ענה."
