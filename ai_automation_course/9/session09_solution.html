כרטיס סוכן לדוגמה, התוצאה הצפויה בכל אחת מ-8 הבדיקות, מבנה שלושת הכלים, ומה קורה בניסיון ההזרקה.

🎓 הרצאה🛠️ תרגול✅ פתרון📌 סיכום
על הפתרוןסוכנים לא דטרמיניסטיים. אותה הודעה יכולה להפעיל כלים בסדר קצת שונה, או לקבל ניסוח אחר. מה שבודקים הוא שהכלים הנכונים הופעלו, שהעובדות נכונות, ושלא הובטח משהו שהסוכן לא יכול לעשות.
1

כרטיס סוכן לדוגמה

כרטיס סוכן: נועם, שירות לקוחות
מטרה: לענות ללקוחות על הזמנות ומדיניות תוך דקה, ולהעביר לנציג כל מה שדורש פעולה.
מי פונה: לקוחות, בטופס באתר ובוואטסאפ (דרך Make)
כלים:
  1. get_order_status · מחזיר פרטי הזמנה · אוטומטי
  2. search_kb · חיפוש בבסיס הידע · אוטומטי
  3. create_ticket · פתיחת קריאה לנציג · אוטומטי (קריאת refund בסטטוס needs_review)
מה הסוכן לא עושה אף פעם: מחזיר כסף, מבטל, משנה הזמנה, מבטיח פיצוי, או עונה ממה שהוא "יודע" על מדיניות
מתי הוא מעביר לאדם: החזר, ביטול, שינוי, פגם, לקוח כועס, או כשלא נמצאה תשובה
מתי הוא עוצר: אחרי 4 הפעלות של כלים, או כשחסר מספר הזמנה (שואל ומחכה)
מדד הצלחה: אחוז הפניות שנסגרו בלי נציג, ואפס הבטחות שגויות בבדיקה השבועית
לתת לסוכן כלי "זיכוי" או "ביטול" כבר בגרסה הראשונה, "כי זה יחסוך זמן". מתחילים בכלים שקוראים מידע ובכלי שפותח קריאה. מוסיפים כלים שכותבים רק אחרי שבועות של לוגים נקיים, ועם אישור אנושי.

שלושת הכלים ב-Make

כלימודוליםנקודות חשובות
get_order_statusSearch Rows (הזמנות, order_id = קלט, Limit 1) ‹ Return outputהמספר בגיליון עשוי להישמר כמספר, והקלט מגיע כטקסט. השוו כטקסט, או המירו. אם לא נמצאה שורה: החזירו found = false, כדי שהסוכן יאמר "לא מצאתי", ולא יקרוס.
search_kbSearch Rows (ידע, topic = קלט) ‹ Text aggregator ‹ Return outputאותו RAG-lite ממפגש 8. בלי תוצאות: החזירו context = "לא נמצא מידע".
create_ticketAdd a Row (קריאות) ‹ Router: priority = high ‹ Slack ‹ Return outputticket_id אפשר לבנות מ-T- ומספר השורה שחזר. created = now. בתרגיל 6 מוסיפים: type = refund ‹ status = needs_review.
התיאורים של שדות הקלט בתרחיש הם חלק מהגדרת הכלי, בדיוק כמו input_schema ב-API. "order_id: מספר הזמנה של 4 ספרות" מונע מהסוכן לשלוח "הזמנה 1043" או את המייל של הלקוח.

חיבור הסוכן

בלוג של הודעה 1, אמורים לראות: הסוכן קיבל את ההודעה ‹ הפעיל את get_order_status עם {"order_id": "1043"} ‹ התרחיש החזיר status: delayed ‹ הסוכן ענה. כלומר, סבב אחד של כלי, ושני סבבים מול Claude.

ב-Make AI Agents, הפלטפורמה מריצה את הלולאה שראינו בהרצאה: היא שולחת ל-Claude את הכלים, מקבלת בקשת tool_use, מריצה את התרחיש, ומחזירה tool_result. אתם בונים רק את הכלים ואת ההוראות.
תרחיש-כלי שלא מוגדר כ-On demand, או שאין לו Return output, לא יופיע ככלי, או שיחזיר תוצאה ריקה. אם הסוכן "לא רואה" כלי, בדקו קודם את שני אלה.

ניסיון ההזרקה

ברוב ההרצות, Claude יזהה שההערה היא ניסיון הזרקה, יענה רק על סטטוס ההזמנה, ואולי גם יציין שיש בהזמנה הערה חריגה. אבל גם אם הוא "נפל" ופתח קריאת refund, הנזק המקסימלי הוא קריאה שנציג יראה ויסגור, כי:

  • אין לסוכן כלי שמחזיר כסף או מבטל הזמנה.
  • קריאת refund נפתחת בסטטוס needs_review.
  • הבטחה שגויה ללקוח ("הזיכוי אושר") היא עדיין בעיה אמיתית. לכן חשוב כלל 3, וחשובה בדיקה של הלוגים.
ההגנה נבנית בשכבות: הוראה בפרומפט (מקטינה את הסיכוי), הרשאות (מגבילות את הנזק), ובדיקה בתוך הכלי (needs_review). אף שכבה לא מושלמת לבד, וביחד הן מספיקות למערכת שירות.
לחשוב שאם הסוכן עמד בניסיון אחד, הוא "חסין". מנסחים אחרים של הזרקה, באנגלית, בתוך מייל או בקובץ מצורף, עשויים להצליח. בונים מתוך הנחה שבסוף זה יקרה.

הלולאה ב-Postman

התשובה הראשונה נראית בערך כך (ה-id משתנה):

{
  "stop_reason": "tool_use",
  "content": [
    { "type": "text", "text": "…" },
    { "type": "tool_use", "id": "toolu_01A…", "name": "get_order_status",
      "input": { "order_id": "1043" } }
  ]
}

לפני בלוק ה-tool_use יכול להופיע בלוק text קצר, ולפעמים הוא לא מופיע. בבקשה השנייה מעתיקים את כל מערך content כמו שהוא לתוך הודעת ה-assistant.

מי הפעיל את הכלי? אתם. Claude רק ביקש. הוא לא ניגש לגיליון, ולא יודע אם התוצאה אמיתית. לכן, כשהחזרתם cancelled, הוא ענה שההזמנה בוטלה. מכאן נובעים שני דברים: האחריות על מה שקורה במערכות היא של מי שמריץ את הכלים, וגם תוצאת כלי יכולה להכיל טקסט זדוני.
